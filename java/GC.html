Mark & Sweep Algorithm

This is the foundation of Java Garbage Collection.

Mark & Sweep Algorithm

✅ How it works (Step by Step)

Step 1: Mark phase
  • GC starts from GC Roots
  • Marks all reachable objects as alive
Step 2: Sweep phase
  • Scans heap
  • Deletes unmarked objects
Visual
[A ✅]   [B ✅]   [C ❌]   [D ✅]   [E ❌]
Sweep removes → C, E

✅ Pros

  • ✅ Simple
  • ✅ No extra memory needed
  • ✅ Works well with reachability analysis

❌ Cons (VERY IMPORTANT)

  • ❌ Stops The World
  • ❌ Memory fragmentation
[A][ ][B][ ][D][ ]

Small holes between objects

Hard to allocate big objects later

  • ❌ Allocation becomes slow

✅ Where used

  • Older JVMs
  • Still used conceptually

Mark, Sweep & Compact Algorithm

This solves the main problem of Mark & Sweep

✅ How it works

Step 1: Mark

Same as before

Step 2: Sweep

Delete garbage objects

Step 3: Compact
  • Move remaining objects together
  • Remove memory gaps
Visual
Before:
[A][ ][B][ ][D]
After Compaction:
[A][B][D][ ][ ]

✅ Pros

  • ✅ No fragmentation
  • ✅ Better memory utilization
  • ✅ Faster object allocation after GC

❌ Cons

  • ❌ Moving objects is expensive
  • ❌ Application paused longer
  • ❌ Object references must be updated

✅ Where used

  • ✔ Old Generation
  • ✔ Full GC scenarios

Copying Algorithm ( MOST IMPORTANT )

Used in Young Generation

Copying Algorithm means we are copying the alive objects in Young Generation from Eden Space to Survivor Space.

✅ Basic Idea

Instead of deleting garbage
👉 Copy only alive objects
Garbage is ignored

✅ Heap Structure for This

Young Generation:

  • Eden
  • Survivor S0
  • Survivor S1

✅ How it works

1.Objects created in Eden

2.Minor GC runs

3.Alive objects copied:

  • From Eden → S0

4.Eden cleared completely ✅

Next GC:
  • Alive objects from S0 → S1
  • S0 cleared
  • Flip spaces
Visual
Before GC:
Eden:   A   B   C ❌   D ❌
After GC:
Survivor:   A   B
(No sweeping required)

✅ Pros

  • ✅ Very fast
  • ✅ No fragmentation
  • ✅ Simple allocation (just copy)

❌ Cons

  • ❌ Extra memory required (2 survivor spaces)
  • ❌ Not suitable for long-living objects

CMS (Concurrent Mark Sweep) – Deprecated

✅ What problem it solved?

Reduce long pause time of Old Gen GC.

✅ How it works

  • Mark & Sweep
  • Runs concurrently with application threads

✅ Pros

  • ✅ Low pause time
  • ✅ Good for interactive apps

❌ Cons

  • ❌ Fragmentation (no compaction)
  • ❌ Complex
  • ❌ Deprecated

GC Algorithm Comparison

GC Algorithm Applied in Young Generation? Applied in Old Generation?
Mark & Sweep ❌ No ✅ Yes (historically / conceptually)
Mark, Sweep & Compact ❌ No ✅ Yes
Copying Algorithm ✅ Yes ❌ No

Young Generation vs Old Generation & Object Promotion

👉 Young Generation uses Copying
👉 Old Generation uses Mark–Sweep–Compact

Why Mark & Sweep is NOT used in Young Generation

Nature of Young Generation
  • Very small
  • Objects die very quickly
  • GC runs very frequently
Problem with Mark & Sweep in Young Gen
  • Leaves fragmentation
  • Requires scanning heap again to allocate memory
  • Too slow for frequent GC
❌ Bad choice for Young Generation

How objects move from Young Generation to Old Generation

If Young Gen uses Copying and Old Gen uses Mark–Sweep–Compact, how do objects move from Young Generation to Old Generation?

The answer is:

👉 Object Promotion (also called Tenuring)

✅ Object Age Concept

Each object has an age counter (not reference count).

Age = number of Minor GCs survived

Example:
  • After 1st Minor GC → age = 1
  • After 2nd Minor GC → age = 2
  • ...

4️⃣ Promotion Rule (HOW Object Moves to Old Gen)

An object is promoted to Old Generation when ANY ONE of these conditions is true 👇

✅ Rule 1: Age Threshold Reached (Tenuring Threshold)

JVM has a parameter:

-XX:MaxTenuringThreshold

Default value: 15

Meaning:

If an object survives 15 minor GCs, it moves to Old Gen

Flow:
Eden → S0 (age 1)
S0 → S1 (age 2)
S1 → S0 (age 3)
...
age == threshold → Old Gen
✅ This is the normal and most common path

✅ Rule 2: Survivor Space Is Full (Premature Promotion)

If Survivor space does not have enough space:

👉 JVM directly promotes object to Old Gen

Why?
  • Copying Algorithm needs free space
  • If Survivor is full → cannot copy
✅ This avoids GC failure
❌ But too many such promotions can cause Old Gen pressure

Traditional GC — How it actually works (baseline)

Traditional Generational GC layout

Heap

┌────────────────────────┐
│ Old Gen │ ← large, long-living objects
│ │
├────────────────────────┤
│ Survivor S1 │
├────────────────────────┤
│ Survivor S0 │
├────────────────────────┤
│ Eden │ ← new objects
└────────────────────────┘

Traditional rules

  • Young Gen
    • Uses Copying algorithm
    • Minor GC → fast, frequent
  • Old Gen
    • Uses Mark → Sweep → Compact
    • Major / Full GC → slow
✅ This design worked fine when heaps were small

2️⃣ The REAL problems in Traditional GC (this is the key)

Let’s not talk theory — let’s talk what breaks in production.

❌ Problem 1: Old Generation is ONE BIG BLOCK

Traditional GC sees Old Gen like this:

[ Old Generation = ONE HUGE AREA ]

When Old Gen is full or fragmented:

👉 GC must:

  • Stop the application
  • Scan the ENTIRE Old Gen
  • Mark everything
  • Sweep everything
  • Compact everything
⛔ No partial cleanup
⛔ No prioritization

❌ Problem 2: Long Stop-the-World pauses

Example:

  • Heap size: 16 GB
  • Old Gen is nearly full

Traditional GC:

“Stop all threads, I need time…”

⏳ Pause = seconds

For:

  • Banking APIs
  • Trading
  • User-facing apps
👉 Unacceptable

❌ Problem 3: No control over pause time

Traditional GC cannot answer this:

“Can you clean memory within 200 ms?”

It doesn’t know.

It just:

  • Starts GC
  • Finishes when it finishes
❌ No predictability

❌ Problem 4: Full GC is ALL or NOTHING

If promotion fails or memory is fragmented:

👉 FULL GC
Stop app
Clean entire heap
Resume

Even if:

  • Only 5% garbage exists
❌ Overkill
G1 GC — comes to picture now

What G1 changes (step by step)

✅ Change #1: Break heap into SMALL REGIONS

Traditional GC:

Young = fixed area
Old = fixed area

G1 GC:

Heap → many small regions (1–32 MB)

Example:

[R1][R2][R3][R4][R5]
[R6][R7][R8][R9][R10]

Each region can be:

  • Young
  • Survivor
  • Old
  • Empty
✅ No giant Old Gen anymore

✅ Change #2: Measure garbage PER REGION

G1 tracks:

“How much garbage is in each region?”

Example:

  • Region R1 → 80% garbage ✅
  • Region R2 → 10% garbage ❌
  • Region R3 → 70% garbage ✅

✅ Change #3: Collect GARBAGE FIRST (name comes from here)

Instead of:

“Clean the whole Old Gen”

G1 says:

“Clean R1 and R3 only — they give max benefit”
  • ✅ Less work
  • ✅ Smaller pause
  • ✅ Faster reclamation

✅ Change #4: Predictable pause time

You can tell G1:

Max pause time = 200 ms

G1 calculates:

  • How many regions it can clean within 200 ms
  • Cleans only that many
⛔ It stops before exceeding pause time

Traditional GC cannot do this.

✅ Change #5: Incremental Old Gen cleanup

Traditional:

Old Gen cleaned → all at once

G1:

Old Gen cleaned → bit by bit → region by region
  • ✅ No massive Full GC
  • ✅ Old Gen cleanup is incremental

6️⃣ Why G1 still uses same algorithms (but smarter)

Important point:

G1 does NOT invent new algorithms.

It still uses:

  • Copying for young regions
  • Mark + Copy/Compact for old regions
💡 Difference is “WHERE and HOW” they are applied

Traditional:

  • Algorithm applied to whole generation

G1:

  • Algorithm applied to selected regions

ZGC – Why it was introduced

Even G1 GC, though much better than traditional GC:
  • Still has Stop-the-World pauses
  • Pause time is low but not zero
  • Object relocation (compaction) still pauses app

For some systems, even 100–200 ms pause is too much:

  • Trading systems
  • Real-time pricing
  • Low-latency APIs
  • Huge heaps (50GB, 100GB)
💡 ZGC was created to make GC pauses almost invisible.

2️⃣ ZGC – Core idea (only ONE sentence)

ZGC runs garbage collection, object movement, and compaction while the application is still running.

That’s it.
That’s the breakthrough.

4️⃣ What ZGC changes (THIS is the magic)

Application keeps running
GC works in parallel
Objects move while app runs
References fixed live
✅ Stop-the-World pauses become very small (1–10 ms)

What is PermGen

✅ Definition (from scratch)

PermGen (Permanent Generation) is a JVM memory area used to store class metadata.

It existed in:

  • Java 6
  • Java 7
  • ❌ Removed in Java 8

Before understanding PermGen, first understand what kind of data the JVM stores.

JVM stores two very different things

✅ 1. Objects (runtime data)

  • new User()
  • ArrayList, String, DTOs, etc.
👉 These go to the Heap

✅ 2. Class-related information (metadata)

When JVM loads a class, it must store:

  • Class name
  • Methods
  • Fields
  • Bytecode
  • Constant pool
  • Annotations
  • Static variables
👉 This is NOT object data
👉 This is class metadata

✅ JVM needed a separate memory area for this.

3️⃣ Where does PermGen exist in JVM memory?

PermGen was inside the JVM-managed memory, alongside the heap.

JVM Memory
├── Heap
│    ├── Young Generation
│    └── Old Generation
│
└── PermGen ✅
✅ PermGen was not Young or Old
✅ It was its own separate space

5️⃣ How does data enter PermGen?

Very important.

When does PermGen grow?

Whenever JVM:

  • Loads a new class
  • Loads a framework
  • Creates a dynamic proxy
  • Uses reflection
  • Uses custom class loaders

Example:

Class.forName("com.myapp.Service");
👉 Metadata of Service goes into PermGen

6️⃣ Is PermGen managed by GC?

✅ YES – 100%

This is a key point.

How GC interacts with PermGen

  • GC does class unloading
  • If a ClassLoader becomes unreachable
  • All classes loaded by it can be removed
  • PermGen memory can be reclaimed
Example (simplified flow)

ClassLoader → loads classes

PermGen → stores metadata


ClassLoader unreachable

↓

GC detects it

↓

Classes unloaded

↓

PermGen memory freed ✅

So yes:
✅ PermGen is part of GC

7️⃣ Then what was the BIG problem with PermGen?

PermGen had ONE MAJOR DESIGN FLAW.

❌ Fixed size

It had a fixed maximum size.

Controlled by:

-XX:MaxPermSize

If you didn’t size it correctly → 💥

8️⃣❌ Why PermGen became a big issue in real projects?

Modern Java apps:

  • Spring
  • Hibernate
  • App servers
  • Hot redeployments
  • Dynamic proxies
  • Bytecode generation

They:

  • Load lots of classes
  • Sometimes don’t unload class loaders properly
Result:
👉 PermGen fills up even though Heap has space

9️⃣ Common PermGen Error (Very Famous)

java.lang.OutOfMemoryError: PermGen space

This error:

  • Had NOTHING to do with heap size
  • Could appear even if heap is mostly free

Why PermGen was REMOVED in Java 8

Oracle realized:

  • Fixed-size metadata space is a bad idea
  • Modern apps load classes dynamically
  • PermGen tuning is painful
✅ Solution = Metaspace

Metaspace (Java 8+)

So when people said:

“PermGen is inside Method Area”

❌ That wording is slightly wrong

✅ Correct wording is:
PermGen implemented the Method Area

2️⃣ Before Java 8: PermGen (why it failed)

  • Class metadata was stored in PermGen
  • PermGen was:
    • Inside JVM memory
    • Fixed size
    • Hard to tune
    • Frequently overflowed
Result:

OutOfMemoryError: PermGen space
  • ❌ Even when heap had free memory
  • ❌ Especially bad for Spring / Hibernate / Tomcat
Metaspace is the JVM’s actual memory implementation of the Method Area (from Java 8 onward).

Java 8+ solution: Metaspace ✅

Method Area (concept)
↓
Metaspace (actual memory)

6️⃣ Where Metaspace lives (THIS IS KEY)

❌ Metaspace is NOT in the Java Heap
✅ Metaspace lives in native (OS) memory
JVM Process Memory

Heap
├── Young Generation
└── Old Generation

Native Memory
├── Metaspace ✅
├── Thread Stacks
└── Direct Buffers

This is why Metaspace:

  • Can grow dynamically
  • Is not limited by -Xmx

8️⃣ How Metaspace works (step by step)

Step 1: Application starts
  • JVM loads core classes (Object, String, etc.)
  • Metadata stored in Metaspace
Step 2: Framework loads classes

(Spring, Hibernate, proxies)


ClassLoader loads class
↓
Metadata allocated
↓
Metaspace grows
✅ JVM requests native memory from OS as needed
👉 gets memory from the OS, not directly from RAM.

So when we say:
“JVM requests native memory from OS”

It means:
JVM asks the OS:
“Please give me some RAM for my internal usage.”
Step 3: Application runs
  • More classes → Metaspace expands
  • No fixed upper limit by default
Step 4: Class unloading (GC interaction)

Metaspace is managed by GC, but differently.

GC does class unloading, not object deletion.

Metadata is freed ONLY IF:

  1. Class is no longer needed
  2. Its ClassLoader becomes unreachable
ClassLoader unreachable
↓
GC detects it
↓
Classes unloaded
↓
Metaspace memory released ✅
If ClassLoader is still referenced → ❌ no cleanup
